上一篇文章讲了三条心法：写作是思想整理术、写你知道的、持续写比写好重要。心法解决的是"敢不敢写"的问题。这篇解决"怎么写"——从你脑子里有一个模糊的想法，到它变成一篇能发出去的文章，中间到底要走哪些步骤。

先给结论，整个流程六步：

**选题 → 定读者 → 搭结构 → 动笔 → 反馈 → 发布**

![新手写作六步法](https://overimages.oss-cn-beijing.aliyuncs.com/images/writing-workflow.webp)

下面每一步都讲清楚"做什么"和"不做什么"。你可以把这篇当清单用：写下一篇文章的时候，按顺序过一遍。

写作六准备：一个真实的问题

传统写作教学会让你先"积累素材""列阅读清单"。写技术博客不需要这些。你只需要一件东西：：*一个你最近真实遇到的问题，和你解决它的过程程*。如果你暂时没有，去翻你的聊天记录、搜索引擎历史、甚至 GitHub issue——你上周查过的那个报错，就是选题。

等等，你可能会问：那你这篇文章里引用的那些书和文章，是什么时候找的？写作过程中找的，不是开工前囤的。动笔时发现某个观点需要出处，就去查证它——查证是写作的一部分，不是准备的一部分。开工前你需要准备的，只有那个真实的问题。

步路线第一步：选题

MManning 出版社的《[Writing for Developers: Blogs that get read](https://livebook.manning.com/book/writing-for-developers/)里有一句话值得抄下来：：*选题是唯一最重要的事。。* 一个平庸的选题，再好的文笔也救不回来；一个戳中痛点的选题，稍微粗糙的句子读者也能忍。

上篇心法二讲过，最好的选题从你自己的经历里长出来，适合新手的类型有六种。这篇把它们展开一点，让每种都具体到"能写什么"：

1.  *你刚修好的一个 bugg*——怎么发现、怎么排查、怎么修复。技术文章里最好写也最容易引起共鸣的一种，因为你刚经历完，记忆还热乎，踩过的坑一个都忘不了
2.  *一个设计决策策*——两个方案里你为什么选了 A，放弃了什么。技术圈聊"方案对比"永远不缺观众，比如"为什么我把博客从 WordPress 迁到了 Hugo"3.  *一个工具的实际用法法*——你摸索出来的配置、你踩过的坑、你的快捷键习惯。工具文是新手最容易写出干货的类型，因为"配置"只有亲手配过的人才讲得出细节
3.  *一次迁移或重构构*——从旧方案迁到新方案，中间断了多少根弦。迁移过程天然有故事感：为什么迁、怎么迁、迁完后悔什么
4.  *能力澄清清*——"X 到底是什么"，你用自己的话讲一遍。讲清楚一个概念，帮到的是所有困惑的人，你的理解也会在这个过程中真正成型

5. **踩坑预防**——"再来一次我会怎么避免"。每个坑都是一篇现成的文章，你踩过的坑，别人大概率正在踩

顺着这六种，三个筛选标准，帮你把候选想法筛成值得写的文章：

- **"3 个月前的我会搜这个吗？"** 会，就写。这是新手期最好的选题测试——你觉得简单的内容，对搜到它的新手是救命稻草
- **"我脑子里有画面吗？"** 提到这个选题，眼前能不能浮现一个具体场景——一个报错、一次卡壳、一张对比截图？能，就写。如果只有概念、没有画面，这不代表选题不好，更可能说明你还没真正动手做过——那样写出来容易空。先去做一遍，再回来写，文章会扎实得多
- **"写出来对谁有用？"** 哪怕只对一个人有用，也值得写

反过来说，有三种选题新手先别碰：纯理论科普（竞争太激烈，新手没优势）、大而全的入门教程（"从零开始学 X"这种，写着写着就放弃了）、纯个人感慨（没有信息量，读者没有理由看）。

## 第二步：定读者

这是新手最常跳过的一步，也是决定文章生死的一步。**不知道写给谁，就不知道写多深。**

一个立刻能用的方法：把读者想象成"**3 个月前的你**"。

- 3 个月前的你，知道"部署"是什么意思吗？知道，就不用解释；不知道，就用一句话带过
- 3 个月前的你，卡在哪个环节？那正是这篇文章要重点写的地方
- 3 个月前的你，会被什么例子打动？就用那个例子

除了"3 个月前的自己"，还有两个更具体的办法：

- **代入一个你认识的人**。想一个真实存在的人——刚入职的同事、带过的实习生、在群里问过你问题的人。想象你是在给他写，他会在哪个环节皱眉头，就重点写哪里。真人比"3 个月前的自己"更好使，因为你真的知道他卡在哪
- **从搜索场景反推**。读者会在什么情况下搜到这篇文章？他当时正在做什么、被什么问题卡住？比如写"如何排查 Nginx 502"，读者大概率是刚被 502 气到摔键盘的人——那他需要的是立刻能上手的排查步骤，不是 Nginx 的历史沿革。这个方法顺带帮你校准了文章的深度

"3 个月前的自己"是默认选项，代入真人更具体，搜索反推更客观。三个方法不冲突，可以混着用。

把这个"读者画像"写在文章开头的注释里（或草稿最上面），提醒自己：整篇文章只对他说话，直到文章写完后再删除。新手最常见的失败，是文章开头对着初学者讲基础，后半段突然跳到一个只有老手才关心的深度优化——因为他没有锁定读者，写到哪算哪。

## 第三步：搭结构

阮一峰在[《技术写作的首要诀窍》](https://ruanyifeng.com/blog/2024/01/weekly-issue-288.html)里给过一个比喻，我强烈建议你记住：**文章是一条单线的游览路线**——"只有一个入口到出口的单一游览路线，跟着箭头一路走，就能看到所有景观"；如果多条路线交叉，"游客非串线不可"。一篇文章只讲一件事，线性推进，由浅入深。

把这个原则落地，给你一个新手可以直接套的五段式骨架：

| 段落     | 作用         | 内容                  |
| ------ | ---------- | ------------------- |
| ① 动机   | 为什么碰这件事    | 一个具体场景，而不是"最近有个需求"  |
| ② 方案   | 为什么放弃别的    | 你试过/看过什么，为什么不用      |
| ③ 实现   | 怎么做        | 关键代码/配置片段，删掉噪音，只贴精髓 |
| ④ 效果   | 做成什么样      | 运行结果、截图、对比          |
| ⑤ 坑与反思 | 哪卡住了，下次怎么办 | 最有价值的部分，别省          |

这个骨架的神奇之处：**它强制你的文章是一条单线**。五段都写完，文章自然有头有尾。如果你发现某个话题五段撑不下——比如光是"实现"就有三个大分支——那就说明该拆成两篇了。这是好事，不是失败。

写大纲还有两个小技巧：

- **每段标题用"动词+对象"**，比如"排查镜像源超时"而不是"关于镜像源"——读者扫一眼就知道这段讲什么
- **大纲写到"小标题 + 每段一句话要点"就停**，不要在大纲阶段就开始雕琢句子，那是动笔阶段的事

## 第四步：动笔

结构定了，动笔其实是最机械的一步。三条规则：

**规则一：开头用倒金字塔。** 最重要的信息放最前面。[freeCodeCamp 的文章](https://www.freecodecamp.org/chinese/news/how-to-write-a-great-technical-blog-post)讲得很直白：技术文章应该"所见即所得"，不要靠悬念吊胃口。一个可以照抄的开头公式：

> 问题（1-2 句）→ 我用了什么方案（1 句）→ 结果如何（1 句）→ 本文讲什么（1 句）

比如："我的网站最近频繁 502。查了两天日志，最后发现是 Nginx 的 keepalive 配置有问题。这篇记录排查过程，以及最后总结的检查清单。"四句话，读者已经知道这篇值不值得读。

**规则二：中间靠标题撑。** 大量使用二级三级标题、列表、代码块，让读者能扫读、能跳读、能定位。技术文章读者 90% 是来"找答案"的，不是来"品鉴"的。

**规则三：代码即证据，但只贴需要的部分。** 贴代码的目的是让读者复现你的过程，不是展示你的全部代码。贴之前问自己：这一段如果删掉，读者还能不能跟上？能，就删。

动笔时还有一个心态技巧：**先写完，再写好。** 一口气把五段骨架填完，哪怕句子很糙。第一稿的任务是"有"，不是"好"。改稿永远比从零写容易，一个不完美的初稿是无价之宝。

## 第五步：反馈

初稿完成，别急着发。先做两件事：

**自己冷读一遍。** 至少隔几个小时（最好隔一天），然后把文章读出来——不用很大声，关起门来读，或者压低声音读，能让自己听见就行。你会听到所有卡顿的地方：那些读起来别扭的句子，就是读者会卡住的地方。改到能一口气读完为止。这个"冷读法"成本为零，但效果惊人——眼睛会跳行，耳朵不会。耳朵是你在这条路上最诚实的审稿人。

**找一个"不知道你在写什么"的人看。** 这个人可以是同事、朋友、论坛上的陌生人。注意一个关键技巧：**不要先告诉他你的写作目标，把草稿原封不动给他，然后问他从中得到了什么。** 这是 [freeCodeCamp 那篇文章](https://www.freecodecamp.org/chinese/news/how-to-write-a-great-technical-blog-post)里推荐的方法。如果他说出的东西和你想表达的差得远，说明文章没有实现目标，改——而不是解释给他听。你不可能在文章旁边站着给每个读者解释，所以草稿必须自己站得住。

技术社区的反馈还有一个独特的好处：**评论区会指出你的错误。** 不要怕，这是免费的技术评审。被指出错误后，改文章、在文末补充"感谢读者指正"，你的文章会越来越硬，读者也会越来越信任你。

## 第六步：发布

技术写作的最后一公里，四个动作：

1. **标题**：包含关键词，让人一眼知道文章讲什么。一个公式："如何 + 具体动作"，比如"如何排查 Nginx 502"。别用"我的踩坑日记"这种谜语式标题——搜索引擎和读者都不喜欢猜谜
2. **配图**：至少一张封面图，正文里配一两张截图。截图比示意图好，示意图比没有好
3. **校对**：错别字、标点、中英文空格。中文写作规范我上一篇文章提过，这里不重复
4. **选平台**：发在哪？个人博客（你的地盘）、掘金/知乎/博客园（中文技术社区流量大）、GitHub（开源项目的配套文档）。新手建议先发社区，因为有人看、有反馈——发完顺手在文末挂一个"原文链接"引流回自己的博客

最后提醒一件事：**发布不是终点。** 过两周回来看看评论，回复每一个认真提问的人；发现自己文章里的错误，马上改。一篇好文章是长出来的，不是生出来的。

## 回顾：六步路线

- **选题**：你最近解决的问题，测试标准是"3 个月前的我会搜吗"
- **定读者**：写给 3 个月前的你
- **搭结构**：五段式骨架（动机→备选→实现→效果→坑），一篇文章一条线
- **动笔**：倒金字塔开头，先写完再写好
- **反馈**：冷读一遍 + 找不知情的人看，别解释目标
- **发布**：标题带关键词、配图、校对、发社区
